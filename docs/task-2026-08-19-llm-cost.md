# Оптимизация расхода LLM и SpeechKit (сообщение в чат 19.08.2026)

Ответ на пять пунктов. Код: `app/services/tts.py`, `app/services/llm.py`,
настройки — `app/config.py` / `.env.example`, тесты — `tests/test_llm_cost.py`
(18 штук, сеть подменена). Все меры включены по умолчанию и все откатываются
переменной окружения, без релиза.

## П.1. SpeechKit API v3

Синтез переехал на `POST https://tts.api.cloud.yandex.net/tts/v3/utteranceSynthesis`
(`_fetch_v3`). Что поменялось по сравнению с v1, кроме тарификации:

- параметры голоса переехали в список `hints` (`{"voice": …}`, `{"role": …}`,
  `{"speed": …}` — по одному полю в элементе, в proto это `oneof`);
- формат задаётся контейнером-перечислением (`MP3` / `OGG_OPUS` / `WAV`), а не
  строкой `format` + `sampleRateHertz`. Побочный плюс: `wav` теперь настоящий
  WAV с заголовком, а не сырой lpcm, который мы клали в файл `.wav`;
- добавлена нормализация громкости `LUFS` — реплики перестают скакать по
  громкости между собой;
- ответ приходит **потоком** JSON-сообщений с кусками аудио в base64, их надо
  склеивать (`_parse_v3_stream`). Заодно оттуда берётся длительность
  (`startMs`/`lengthMs`) — раньше `duration_ms` был оценкой «14 символов в
  секунду», теперь это факт. Разбирается и вариант «один цельный JSON» — так
  отвечает API Gateway на коротком синтезе.

Пустой ответ (200 без единого `audioChunk`) — это `UpstreamError`, а не файл на
0 байт: иначе фронт показывает битый плеер вместо понятной ошибки.

Откат: `SPEECHKIT_API_VERSION=v1`. Путь v1 остался рабочим и неизменным —
`folderId` в теле, форма, без `x-folder-id`, — так что откат возвращает ровно
тот запрос, который крутился на проде.

## П.2. Нормализация чисел — на lite

`llm.to_spoken_text` («Пётр I» → «Пётр Первый») ходит на lite-модель. URI
берётся из `YANDEXGPT_LITE_MODEL_URI`, а если он пуст — выводится из основного
заменой `yandexgpt` → `yandexgpt-lite`. Для дообученной модели (`ds://…`)
подстановка не срабатывает и запрос идёт на основную — лучше заплатить, чем
уйти в несуществующую модель.

Качество подстраховано с двух сторон и без нас: `tts.prepare_for_tts`
отбрасывает ответ, который втрое длиннее исходного текста, а без LLM работает
детерминированный `normalize_for_tts`. Плюс кэш по хэшу текста — он был и
раньше, повторные «Прослушать» не оплачиваются.

## П.3. Короче контекст уточняющих вопросов

Две правки в `_yandexgpt_chat`:

- история диалога: `history[-6:]` → `history[-GUIDE_HISTORY_TURNS:]`, по
  умолчанию **3** реплики;
- справка: раньше в промпт уходил весь `short_description + raw_history`
  (бывает несколько тысяч знаков, и это оплачивается на КАЖДОМ уточняющем
  вопросе), теперь — первые `GUIDE_GROUNDING_MAX_CHARS` знаков (700) с обрезкой
  **по границе фразы**. Обрывать на полуслове нельзя: модель додумывает хвост.

Заодно в `app/routers/guide.py` история поднимается из БД сразу хвостом
(`ORDER BY id DESC LIMIT GUIDE_HISTORY_TURNS`): раньше на каждый вопрос
вычитывался весь диалог сессии, хотя в промпт уходили последние реплики.

## П.4. Рассказ вдвое короче

В промпт `_yandexgpt_story` добавлен бюджет объёма: «не больше
`GUIDE_STORY_MAX_CHARS` знаков (примерно 5–7 предложений)» плюс требование не
пересказывать данные подряд и не начинать с «сегодня мы поговорим».
`maxTokens` опущен с 800 до `GUIDE_STORY_MAX_TOKENS=500` — но это именно
страховка над целью, а не сама цель: длину держит промпт, потому что обрезка по
токенам рвёт фразу на полуслове.

## П.5. Логирование расхода

Одна строка `INFO` на каждый платный вызов, формат `key=value` — логи Cloud
Functions ищутся подстрокой:

```
llm_usage operation=chat model=gpt://<folder>/yandexgpt/latest model_version=… input_tokens=412 output_tokens=180 total_tokens=592
tts_request api=v3 voice=alena role=good fmt=mp3 chars=284 duration_ms=19040 bytes=76032
```

`operation` — `story` | `chat` | `questions` | `tts_spoken`: видно не только
сколько потрачено, но и на чём. Выключается `LLM_LOG_USAGE=false`.

## Что стоит увидеть на проде

Меры бьют по разным статьям, и проверяются они тоже по-разному:

| Что смотреть | Как |
|---|---|
| Токены на один ход диалога (п.3) | `llm_usage operation=chat` — `input_tokens` до и после деплоя |
| Токены на рассказ (п.4) | `llm_usage operation=story` — `output_tokens` |
| Доля lite в расходе (п.2) | `llm_usage operation=tts_spoken` — поле `model` |
| Синтез (п.1) | `tts_request api=v3` — число строк = число платных запросов |

Числа экономии в рублях здесь намеренно не приводятся: прайс Yandex Cloud
сверять надо на дату деплоя, а не по памяти. Порядок величин виден из логов
выше в первые же сутки.

## Не входило в пять пунктов, но стоит следующим шагом

**Один ход диалога — это два вызова LLM**: ответ (`operation=chat`) и генерация
вопросов-подсказок (`operation=questions`, `llm.chat` → `_yandexgpt_questions`).
Вторые нужны фронту не на каждом ходу и почти не зависят от реплики — их можно
считать один раз на экспонат и кэшировать (или отдавать `_questions_stub`, он
детерминированный и бесплатный). Это примерно минус треть вызовов LLM в чате;
делать не стал — вне поставленных задач, нужен ответ фронта, готовы ли они
получать `questions: []` на части ответов.
