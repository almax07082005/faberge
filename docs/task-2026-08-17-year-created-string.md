## Решение по п.5 — судьба `dating`: вариант (а), выпилен

`year_created` — единственное поле датировки, строкой, дословно как в
путеводителе («1899–1903», «1880-е», «конец XIX — начало XX века»).
`dating` удалён из БД, модели, схем и openapi. Почему (а), а не «оставить оба»:

- после п.1–2 поля были бы бинарными дублями — два источника правды на одну
  датировку расползаются при первой же ручной правке в админке;
- сортировок и фильтров по числовому году в коде не было ни одного — нижняя
  граница не нужна никому, кроме самого разбора каталожной строки (там она
  осталась внутренним полем `year_lower` — по ней считается точность датировки
  для отчёта бэкфилла);
- фронту одно поле проще (сказано в самой таске).

Переходных мер для старых клиентов две, обе на бэке:

- **int принимается и приводится к строке**: админ-форма до обновления шлёт
  `Number` — получит не 422, а `"1899"` (`YearCreated` в `app/schemas.py`);
- **лишний `dating` во входе игнорируется** Pydantic'ом молча — старый клиент,
  который его ещё шлёт, не ломается (но и не пишет никуда).

Фронту после деплоя: `yearCreated: string`, логика «dating, если заполнен» —
в помойку, поле в выдаче уже готовое к показу.

## Данные (п.2)

Одним оператором в миграции, без окна половинчатого состояния:

```sql
ALTER TABLE exhibits
    ALTER COLUMN year_created TYPE TEXT
    USING COALESCE(NULLIF(btrim(dating), ''), year_created::text);
```

`dating` заполнен → берётся он (полная датировка); пуст → `str(год)`; пусто оба
→ NULL. Проверочные запросы — в самой миграции; там же откат, восстанавливающий
пару 12.08 (единственная оговорка отката описана в его комментарии).

## Импортёр (п.3)

`parse_catalog_line` теперь отдаёт `ParsedLine.year_created` — строку датировки
целиком; нижняя граница переехала во внутреннее `year_lower` (нужна
классификации точности и пометке «перевёрнутый диапазон», в колонки не
пишется). `scripts/backfill_catalog_fields.py` пишет в `year_created` строку;
правило «непустое поле не перезаписываем никогда» и идемпотентность не
изменились.
