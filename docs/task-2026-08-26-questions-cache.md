# Кэширование вопросов-подсказок на экспонаты (просьба в чат 26.08.2026)

> «Давайте сделаем кеширование вопросов-подсказок на экспонаты, можно хранить их
> в бд + сделать разовый прогрев каталога»

Сделано и то, и другое. Код: `app/services/guide_questions.py` (решение
«свежо / пора перегенерировать»), `app/crud.py` (хранилище), `app/models.py` +
`db/schema.sql` + `db/migrations/2026-08-26_exhibit_questions_cache.sql`
(таблица), `app/routers/guide.py` (использование), `app/routers/admin.py` +
`scripts/warm_guide_questions.py` (прогрев). Тесты — `tests/test_guide_questions_cache.py`
(21 штука, без БД и сети). Кэш включён по умолчанию и откатывается переменной
окружения, без релиза.

## Что именно оплачивалось дважды

Вопросы-подсказки считает отдельный вызов YandexGPT — в логах расхода это
`operation=questions`. Он шёл **вторым** рядом с каждым рассказом
(`POST /guide/story`) и рядом с каждой репликой диалога об экспонате
(`POST /guide/chat`): один ход диалога — два вызова LLM.

При этом результат зависит **только от карточки экспоната**. Не от посетителя,
не от истории диалога, не от заданного вопроса — промпт генерации вопросов
собирается из `raw_history` / `short_description` / `name` и больше ни из чего.
Один экспонат за день открывают десятки посетителей, и каждый раз мы платили за
один и тот же текст.

## Устройство

Таблица `exhibit_questions`: `(exhibit_id, language)` → пул вопросов,
`source_hash`, модель, `updated_at`.

**Свежесть — по хэшу, а не по времени.** `source_hash` — sha256 языка и текста,
который уходит в промпт (`llm.questions_source` — та же функция, что и в
генерации, поэтому они не могут разойтись). Музей поправил описание в админке —
хэш разошёлся — запись перегенерируется при первом же обращении. Ручной
инвалидации нет, и TTL нет намеренно: описания правят редко, а «протухание по
времени» просто вернуло бы часть расхода за текст, который не менялся.

**В записи лежит пул, наружу уходит срез.** `GUIDE_QUESTIONS_CACHE_SIZE` (6) —
сколько вопросов просим у модели; `/guide/story` показывает 4, `/guide/chat` —
3. Без пула запрос с `max_questions=3` выбивал бы запись, сделанную для 4, и
кэш грелся бы вхолостую.

Длина набора на свежесть НЕ влияет: `max_questions` — потолок, а не требование.
Модель регулярно отдаёт меньше, чем просили (пять вопросов вместо шести), и
правило «в записи должно лежать ровно столько, сколько попросили» превращало бы
такие карточки в вечный промах — каждый запрос заново платит за набор, который
не вырастет. Это ловилось на живой БД: после прогрева `--dry-run` показывал
«требует генерации: 6 из 11».

**Сбой LLM не роняет рассказ.** Подсказки — не сам ответ гида: если модель
недоступна, а запись есть, посетитель получит прошлый (пусть и устаревший)
набор вопросов. Записи нет — сбой пробрасывается, как и до кэша.

Чего в кэше нет: вопросов в общем чате (без контекста экспоната их не к чему
привязать — их не было и раньше) и кэша по `max_questions` (см. про пул выше).

## Прогрев каталога

Кэш наполняется сам по мере обращений — прогрев нужен, чтобы первый посетитель у
витрины не ждал лишний вызов LLM и чтобы музей мог посмотреть вопросы по всему
каталогу до открытия.

```bash
python scripts/warm_guide_questions.py            # сухой прогон: сколько карточек требует генерации
python scripts/warm_guide_questions.py --apply    # прогреть (один вызов LLM на карточку)
python scripts/warm_guide_questions.py --limit 20 --verbose --apply   # проба
```

Сухой прогон — по умолчанию: прогрев всего каталога это 1200+ вызовов модели, и
решение «жечь токены» принимает человек, а не ключ по умолчанию. Прогон
идемпотентен: карточка со свежей записью пропускается **без** обращения к LLM,
повторный запуск сразу после успешного печатает «сгенерировано: 0». Сбой на
карточке не останавливает прогон — она уходит в «не удалось» и будет взята
следующим запуском.

`--force` нужен в двух случаях: менялся сам промпт генерации вопросов
(`llm._yandexgpt_questions`) или подняли `GUIDE_QUESTIONS_CACHE_SIZE` и нужно
расширить уже записанные наборы. Изменения описаний ловятся хэшем и без него.

Без шелла — из админки, порциями: `POST /admin/guide/questions/warm?limit=25`
(вызывать, пока `status.missing` не станет нулём) и `GET /admin/guide/questions/status`
для покрытия. Порциями — потому что 1200+ вызовов LLM в один HTTP-запрос
функции не укладываются.

## Что видно в логах

`operation=questions` теперь означает **промах кэша**: новая или
отредактированная карточка. У прогретого каталога ход диалога — один вызов
(`chat`), рассказ — один вызов (`story`).

## Порядок на проде

1. `psql "$DATABASE_URL" -f db/migrations/2026-08-26_exhibit_questions_cache.sql`
   (таблица; старый код с ней работает — он её просто не видит);
2. деплой функции;
3. `python scripts/warm_guide_questions.py --apply` — по желанию, кэш наполнится
   и сам.

## Откат

`GUIDE_QUESTIONS_CACHE_ENABLED=false` — гид снова считает вопросы на каждый
запрос, в БД не ходит; таблицу при этом сносить не нужно, накопленные записи
дождутся возврата флага. Полный откат схемы — секция «Откат» в шапке миграции:
таблица только кэш, первичных данных в ней нет.
