# Аналитика посетителей: что храним и как обезличено

Документ фиксирует состав данных, которые бэкенд «ИИ-гида музея Фаберже»
собирает для аналитики (§10 ТЗ от 03.08.2026). Это то, что показывают заказчику
на вопрос «а вы там персональные данные не собираете?».

Дата составления: 03.08.2026. Актуально для схемы после миграции
`db/migrations/2026-08-03_analytics.sql`.

## Коротко

Персональные данные не собираются и не хранятся. Приложение работает **без
регистрации**: у посетителя нет учётной записи, имени, телефона и почты — их
неоткуда взять. Идентификаторы (`session_id`, `device_id`) — случайные UUID,
сгенерированные на клиенте; связать их с человеком нельзя ни внутри системы, ни
join-ом с чем-либо ещё.

## Что храним

### Таблица `events` (телеметрия)

| Поле | Что это | Персональные данные |
|---|---|---|
| `session_id` | Случайный UUID, живёт в `sessionStorage` вкладки | нет |
| `device_id` | Случайный UUID, живёт в `localStorage` устройства | нет |
| `type` | Тип события из закрытого словаря (`app_open`, `hall_view`, …) | нет |
| `exhibit_id` / `hall_id` / `showcase_id` / `label_slug` | Что посетитель открыл | нет |
| `props` | Специфика события — **только ключи из контракта** | см. ниже |
| `ts` | Время действия | нет |

**`device_id` — самое чувствительное, что здесь есть.** Это постоянный
идентификатор, и живёт он ровно ради одной метрики — «сколько посетителей
приходит повторно» (§7 ТЗ). Он не связывается ни с каким профилем, не передаётся
наружу и не участвует ни в одном join-е за пределами `events`.

### Белый список `props`

`props` — свободный JSONB, а `POST /telemetry/events` открыт без авторизации.
Поэтому на приёме работает **белый список ключей по типу события**
(`app/schemas.py`, `EVENT_PROPS_ALLOWED`): всё, чего нет в контракте, молча
отбрасывается и в БД не попадает.

| Тип события | Разрешённые ключи |
|---|---|
| `app_open` | `entry`, `qr_id` |
| `exhibit_view` | `source` |
| `recognition` | `recognized`, `confidence`, `fallback`, `candidates_count`, `retry` |
| `chat_message` | `text` |
| `search_query` | `text`, `results_count` |
| `session_end` | `reason`, `last_screen` |
| `hall_view`, `showcase_view`, `chat_open`, `tts_play` | — (props не используется) |

Явно перечислены и запрещены (`EVENT_PROPS_DENIED`): `user_agent`, `ip`,
`email`, `phone`, `url`, `referrer`, `geo`. Формально это дублирует белый список
— перечислены они затем, чтобы намерение было видно из кода, а не выводилось из
его отсутствия.

`props.text` (текст вопроса или поискового запроса) обрезается до 500 символов.

`recognition.retry` (добавлен 04.08.2026) — флаг «это повторная съёмка после
неудачной попытки», `true`/`false`. Персональных данных не добавляет: он говорит
о предыдущем событии того же визита, а не о посетителе. Нужен затем, чтобы
`retry_after_fail` в отчёте считался по явному признаку от клиента, а не
восстанавливался эвристикой по порядку событий.

### Тексты вопросов

Тексты вопросов посетителей хранятся: в `events.props.text` (событие
`chat_message`) и в `guide_messages.content` — без них невозможны требуемые
заказчиком отчёты «частые вопросы» и «вопросы без ответа гида».

Посетитель может ввести в чат что-то личное по своей инициативе. Здесь действуют
два ограничения:

* текст **не связан ни с каким идентификатором личности** — только со случайным
  `session_id`;
* текст **не попадает в логи** (см. ниже).

### Таблицы агрегатов

`analytics_daily` и `analytics_reports` содержат только посчитанные цифры и
кластеры формулировок вопросов. Идентификаторов сессий и устройств в них нет.

## Чего не храним

* **IP-адрес** — `POST /telemetry/events` не читает адрес клиента и не пишет его
  ни в `events`, ни в логи доступа.
* **User-Agent** — тоже не читается и не сохраняется; ключ `user_agent` в `props`
  отбрасывается белым списком.
* **Геолокация, реферер, URL с параметрами** — не принимаются.
* **Учётные данные посетителя** — их не существует: регистрации нет.

## Логи

Прикладные логи (`logging`) пишутся в `app/routers/recognition.py` и
`app/services/*`. В них попадают: идентификаторы экспонатов, slug'и меток,
уверенность распознавания, сообщения об ошибках внешних сервисов.

**Тексты вопросов, IP и User-Agent в логи не пишутся.** Если в будущем
понадобится диагностировать конкретный вопрос, логируйте длину и хеш текста, а
не сам текст.

## Разделение с админкой

`events` и `guide_messages` не имеют внешних ключей на административные
сущности, а модель администратора в БД отсутствует вовсе (доступ к `/admin/**`
— по статическому Bearer-токену из конфигурации). Джойны «событие ↔
администратор» невозможны технически, а не по договорённости.

## Срок хранения

События **не удаляются** — прямое требование заказчика (аналитика за сезон и
сравнение периодов). Это учтено в индексах (`db/migrations/2026-08-03_analytics.sql`)
и в ночном пересчёте агрегатов: таблица растёт линейно от посещаемости, и
отчёты читают агрегаты, а не сырые события.

Если требование изменится, удаление сырых событий старше N месяцев не сломает
отчёты за прошлые периоды — они уже лежат посчитанными в `analytics_reports`.

## Где смотреть в коде

| Что | Где |
|---|---|
| Словарь типов событий, белый список `props` | `app/schemas.py` — `EventType`, `EVENT_PROPS_ALLOWED`, `EVENT_PROPS_DENIED` |
| Фильтрация на приёме | `app/schemas.py` — `normalize_event`, `clean_event_props` |
| Приём событий | `app/routers/telemetry.py` |
| Схема таблиц | `db/schema.sql`, `db/migrations/2026-08-03_analytics.sql` |
