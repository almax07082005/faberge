# История чатов с ИИ-гидом: как есть и что решаем

Документ отвечает на вопрос заказчика из баг-репорта 06.08.2026, п. 11: «Не доступна
история чатов, если нажать на стрелку назад. Как сейчас можно перейти в историю чатов?
Или чат единственный и сохраняется как сессия одного посетителя?»

Дата составления: 06.08.2026. Код на момент разбора — ветка `main`, коммит
«Аналитика посетителей: контракт событий, метрики визита, отчёты и выгрузка».

## Коротко

**Чат один на визит.** Все реплики уже пишутся на сервер (`guide_sessions` /
`guide_messages`), но **ручки на чтение нет** — наружу история не отдаётся ни в каком
виде. Для посетителя история живёт только во фронте, в браузере устройства.

Рекомендация: так и оставить. Бэкенд трогать не нужно, «назад» и восстановление
переписки — фронтовая часть. Серверный контракт на случай другого решения продукта
описан ниже целиком, чтобы фронт мог начинать в тот же день, когда придёт «да».

## Как есть сейчас

### Что реально пишется на сервер

Пишет одно место — `app/routers/guide.py`, функции `_add_messages` (обычный путь) и
`_persist_messages` (когда дальше отдаётся 502). На каждый обмен уходят **две строки**:
реплика посетителя (`role='user'`) и ответ гида (`role='assistant'`).

`guide_sessions`:

| Поле | Что это |
|---|---|
| `id` | UUID сессии диалога. **Генерирует сервер** (`uuid.uuid4()` в модели / `gen_random_uuid()` в схеме) на первом `POST /guide/chat` без `session_id` и возвращает в `session_id` ответа |
| `context` | JSONB последнего контекста (`exhibit_id`, `label_slug`, `hall_id`) — чтобы «расскажи подробнее» продолжало разговор о том же экспонате |
| `created_at`, `last_activity` | Создание и последняя реплика; `last_activity` обновляется на каждом ответе |

`guide_messages`:

| Поле | Что это |
|---|---|
| `id` | `BIGSERIAL` — монотонный, по нему и восстанавливается порядок реплик |
| `session_id` | FK на `guide_sessions`, `ON DELETE CASCADE` |
| `role` | `user` / `assistant` (`system` разрешён схемой, но сейчас не пишется) |
| `content` | Текст вопроса или ответа, целиком, без обрезки |
| `answered` | Смог ли гид ответить (§4 ТЗ 03.08.2026). Ставится в момент генерации |
| `fail_reason` | Почему не смог: `no_context`, `llm_refusal`, `llm_hedge`, `not_found`, `error`. `llm_hedge` добавлена 31.08.2026 — это ответ по существу с оговоркой, и только она из «неудачных» причин не прячет вопрос из подсказок гида |
| `exhibit_id`, `hall_id` | Контекст вопроса — у какого экспоната/зала спрашивали |
| `created_at` | Время записи |

Три детали, которые видны только из кода и важны для решения:

* `answered`/`fail_reason`/`exhibit_id`/`hall_id` пишутся **на обе строки пары** —
  так отчёт «вопросы без ответа» читает `role='user'` без self-join;
* при сбое LLM пара **всё равно сохраняется** (`_persist_messages`, `answered=false`,
  `fail_reason='error'`) до того, как клиент получит 502 — то есть в истории на сервере
  лежат и неудачные обмены, которых посетитель у себя на экране не видел;
* сервер уже **читает** историю внутри `POST /guide/chat`: если клиент не прислал
  `history`, берётся `SELECT ... WHERE session_id = ... ORDER BY id`, а в промпт уходят
  последние 6 реплик (`app/services/llm.py`, `history[-6:]`). Данные для истории есть,
  не хватает только эндпоинта.

### Сколько живёт и есть ли чистка

Не чистится вообще: TTL нет, ночного джоба нет, `scripts/` не содержит ничего, что
удаляло бы сессии или реплики. Каскад один — удаление `guide_sessions` уносит свои
`guide_messages`. Это согласуется с `docs/analytics-privacy.md` («события не удаляются —
прямое требование заказчика»), но для `guide_messages` это скорее сложилось, чем было
решено: их держат ради отчётов «частые вопросы» и «вопросы без ответа».

### Ручки на чтение действительно нет — проверено, а не со слов

* `app/routers/guide.py` — два обработчика, оба `@router.post`: `/guide/story` и
  `/guide/chat`. `GET` в файле нет ни одного.
* `openapi.yaml` — под префиксом `/guide` объявлены ровно два пути, те же самые.
* Единственные читатели `guide_messages` — административные отчёты в `app/crud.py`
  (`analytics_questions`, `analytics_unanswered`, суточные счётчики). Они за
  Bearer-токеном админки и отдают агрегаты, а не переписку конкретной сессии.

### Где живёт история сейчас

У посетителя — во фронте, в хранилище браузера. Отсюда всё, о чём спрашивает заказчик:

* история есть, **пока не почищено хранилище** (очистка данных сайта, «приватная»
  вкладка, переустановка PWA — и переписки нет);
* она **не переносится между устройствами**: открыл на своём телефоне, продолжил на
  музейном планшете — на планшете чисто;
* на сервере при этом лежит полная копия, к которой у посетителя нет доступа.

### Ещё две вещи, которые всплывут при любом решении

**Неизвестный `session_id` сейчас не 404.** `POST /guide/chat` делает
`session.get(GuideSession, req.session_id)`, и если сессии нет — молча заводит новую и
возвращает её `session_id`. То есть клиент, приславший протухший UUID, получает рабочий
ответ и новую сессию. У читающей ручки поведение будет другим (404), и фронту это надо
знать заранее.

**Сессия гида не связана с устройством.** В `guide_sessions` нет `device_id`, а
телеметрический `session_id` из `events` — **другой** идентификатор (генерируется
клиентом в `sessionStorage`, см. `docs/analytics-privacy.md`) и с `guide_sessions.id`
не совпадает. Связать «все чаты этого устройства» сегодня нечем: это миграция, а не
эндпоинт.

## Решение: чат один на визит

Фиксируем вариант, который автор баг-репорта и предлагает как ставку для музея.

**Почему так:**

1. **Сценарий музея.** Посетитель приходит на один-два часа. Чат — спутник этой
   прогулки, а не переписка, к которой возвращаются через неделю. «Список диалогов»
   решает задачу, которой у посетителя музея нет, зато добавляет экран, состояние и
   навигацию туда, где сейчас одна кнопка «назад».
2. **Приватность.** Тексты вопросов — самое чувствительное, что вообще есть в системе:
   посетитель может по своей инициативе написать в чат что угодно личное
   (`docs/analytics-privacy.md`, раздел «Тексты вопросов»). Сегодня они защищены тем,
   что **наружу их не отдаёт никто**. Публичная ручка чтения переводит защиту из
   «данные не выходят из БД» в «данные выходят, но только тому, кто знает UUID» — это
   принципиально более слабая гарантия, и её придётся обосновывать музею.
3. **Стоимость поддержки.** Ручка чтения тянет за собой то, чего в проекте сейчас нет
   вовсе: срок хранения (сколько история доступна по ссылке), удаление по запросу,
   защиту от перебора и rate limit, а для списка чатов — ещё и миграцию с `device_id`
   и токен устройства. Это несколько дней бэка плюс постоянный хвост в поддержке ради
   сценария из п. 1.

**Что это значит по работам:** бэкенд не меняется. Фронт хранит переписку локально
(как сейчас), по «назад» из карточки экспоната возвращает посетителя в тот же чат с
восстановленной лентой, а `session_id` из ответа `POST /guide/chat` переиспользует,
пока идёт визит, — тогда контекст на сервере тоже остаётся сшитым.

**Что при этом честно не гарантируется:** переписка теряется при очистке хранилища и
не переезжает на другое устройство. Если музей когда-нибудь скажет «посетитель должен
находить свой вчерашний чат» — это ровно вариант ниже, и он готов к запуску.

## Если продукт выберет вариант «список диалогов» — контракт

Всё ниже — предложение к реализации, в коде этого пока нет.

### GET /guide/sessions/{session_id}/messages

Публичный, как и весь `/guide/**` (`security: []`): учётной записи у посетителя нет.

**Параметры**

| Параметр | Где | Тип | По умолчанию | Смысл |
|---|---|---|---|---|
| `session_id` | path | UUID | — | Сессия диалога, та самая из ответа `POST /guide/chat` |
| `limit` | query | int 1..100 | 50 | Размер страницы |
| `offset` | query | int ≥ 0 | 0 | Смещение |
| `order` | query | `asc` / `desc` | `asc` | Порядок по `id`. `desc` — для подгрузки более ранних реплик при скролле вверх |

Сортировка — **по `id`, а не по `created_at`**: вопрос и ответ пары пишутся одним
коммитом и имеют практически одинаковый `created_at`, порядок внутри пары по времени
неустойчив.

**Ответ 200**

```json
{
  "session_id": "2f6a9b3c-1d4e-4f8a-9c2b-5e7a1d0c3b66",
  "created_at": "2026-08-06T11:02:41Z",
  "last_activity": "2026-08-06T11:19:08Z",
  "context": { "exhibit_id": 101, "label_slug": "faberge_egg_coronation", "hall_id": 5 },
  "total": 24,
  "limit": 50,
  "offset": 0,
  "messages": [
    {
      "id": 918234,
      "role": "user",
      "content": "Кому подарили это яйцо?",
      "created_at": "2026-08-06T11:03:12Z",
      "exhibit_id": 101,
      "hall_id": 5
    },
    {
      "id": 918235,
      "role": "assistant",
      "content": "Николай II подарил его императрице Александре Фёдоровне на Пасху 1897 года…",
      "created_at": "2026-08-06T11:03:12Z",
      "exhibit_id": 101,
      "hall_id": 5
    }
  ]
}
```

**Что отдаём и что нет**

| Поле БД | Отдаём? | Почему |
|---|---|---|
| `id`, `role`, `content`, `created_at` | да | Минимум, без которого ленту не нарисовать |
| `exhibit_id`, `hall_id` | да | Фронт восстанавливает по ним плашки и переходы: карточку добирает через `GET /exhibits/{id}` |
| `answered`, `fail_reason` | **нет** | Это внутренняя оценка качества гида для отчётов музея (§4). Посетителю она бесполезна, а подпись «на ваш вопрос гид не ответил» под его же репликой — вредна; `fail_reason='error'` вдобавок раскрывает внутренние сбои. Остаётся в `/admin/analytics/unanswered` |
| `session.context` | да | Позволяет фронту вернуться в чат в том же контексте, в каком его оставили |

Отдельно: `suggested_questions`, `referenced_exhibits` и `location` из ответа
`POST /guide/chat` **не хранятся вовсе** и в истории не восстанавливаются. Если они
нужны в восстановленной ленте, это отдельное решение (хранить JSONB рядом с репликой
ассистента) — по умолчанию не делаем: подсказки к старому вопросу устаревают.

**Коды ответа**

| Код | Когда | Тело |
|---|---|---|
| 200 | Сессия найдена | см. выше; пустой `messages` возможен |
| 404 | Сессии нет **или** она старше срока хранения (см. ниже) | `{"detail": "Сессия не найдена."}` — одинаковое в обоих случаях, чтобы ответ не подтверждал существование сессии |
| 422 | `session_id` не UUID, `limit`/`offset`/`order` вне диапазона | стандартный формат FastAPI |

Заголовок ответа — `Cache-Control: no-store`: переписка не должна оседать в
промежуточных кэшах гейтвея.

### Нужен ли список сессий по `device_id`

**Технически сегодня невозможен** без миграции: в `guide_sessions` нет `device_id`, а
`events.device_id` лежит в другой таблице и рядом с *телеметрическим* `session_id`,
который сессии гида не равен. Понадобится: колонка `guide_sessions.device_id` + индекс,
приём `device_id` в `POST /guide/chat`, и всё равно старые диалоги в список не попадут —
у них привязки нет.

**И это самое опасное место всего варианта.** `device_id` — постоянный анонимный
идентификатор в `localStorage`; в `docs/analytics-privacy.md` он назван самым
чувствительным, что есть в системе, и живёт ради ровно одной агрегатной метрики
(«сколько посетителей приходит повторно»). Публичная ручка `GET /guide/sessions?device_id=…`
превращает его в **ключ доступа**: он не секрет, уезжает в каждом событии телеметрии и
лежит в хранилище браузера, — а по нему будут отдаваться все тексты вопросов этого
человека за всё время. Один анонимный идентификатор, связывающий визиты, плюс доступ к
текстам — это уже профиль.

Поэтому: если список делать, то **не по голому `device_id`**, а по серверному секрету —
непубличному токену устройства, который сервер выдаёт при первом обращении и хранит
хешем. Это отдельное решение и отдельная оценка; в «быстрый вариант Б» оно не входит.

### Авторизация и перебор

`/guide/**` публичный намеренно — у посетителя нет учётной записи, вводить нечего.
Единственный «секрет» — сам `session_id` (UUIDv4, 122 случайных бита), поэтому:

* **перебор нереален** — это не последовательный целочисленный id; угадать живую
  сессию подбором нельзя;
* **реальные риски другие**: утечка UUID вместе со ссылкой (шаринг, история браузера,
  access-логи гейтвея) и сканирование «на удачу», которое данных не даст, но нагрузит БД.

Что с этим делаем:

1. `session_id` — **только в path, никогда в query**: в query он осядет в логах
   гейтвея (тот же принцип, что «никаких персональных данных в query»).
2. **Rate limit** на `/guide/sessions/**` — в приложении его сейчас нет вообще
   (ни middleware, ни зависимости), проще навесить на API Gateway.
3. **404 без различия** «не существовала» / «истекла» — ответ не должен работать
   оракулом существования сессии.
4. **Ограниченный срок жизни** — чем короче окно чтения, тем меньше стоит утёкшая
   ссылка (см. ниже).
5. Никаких чужих сессий: ручка отдаёт ровно ту сессию, чей UUID предъявлен, и не
   умеет ни списка «всех сессий», ни поиска по содержимому.

### Срок хранения и удаление

Сейчас `guide_messages` не удаляются никогда и никем. Как только появляется чтение,
срок хранения перестаёт быть внутренним делом — то, что можно прочитать по ссылке,
надо ограничить во времени. Предложение:

* **читать** можно сессии с `last_activity` не старше **30 дней**; всё, что старше, —
  404. Визит в музей длится часы, месяц — с запасом;
* **хранить** реплики по-прежнему дольше: отчёты «частые вопросы» и «вопросы без
  ответа» строятся за сезон, и их читает только админка;
* `DELETE /guide/sessions/{session_id}` → 204, каскадом сносит реплики. Это же —
  готовый ответ на «удалите мою переписку»;
* ночная чистка — рядом с `scripts/rebuild_analytics.py`, отдельным шагом.

### Оценка работ по бэкенду

| Работа | Оценка |
|---|---|
| `GET /guide/sessions/{id}/messages`: схемы, роутер, crud, `openapi.yaml`, тесты | 0,5–1 день |
| 404 на неизвестную/протухшую сессию, `Cache-Control: no-store`, согласование с поведением `POST /guide/chat` | 0,5 дня |
| `DELETE /guide/sessions/{id}` + ночная чистка старше N дней | 0,5 дня |
| **Итого «быстрый вариант Б»** | **1,5–2 дня** |
| Список диалогов по устройству: миграция `guide_sessions.device_id`, приём `device_id` в чате, токен устройства, ручка списка | +2–3 дня, отдельным решением по приватности |
| Rate limit на `/guide/sessions/**` | вне кода бэка — конфигурация API Gateway |

## Что нужно от продукта

**Вопрос один: чат в приложении — один на визит или список диалогов, который посетитель
может листать и находить на другом устройстве?**

* **Ответ «один на визит» (рекомендация).** Бэкенд не трогаем, задача закрывается на
  фронте: возврат по «назад» в тот же чат и восстановление ленты из локального
  хранилища. Этот документ и есть письменная фиксация решения — п. 11 закрыт.
* **Ответ «список диалогов».** Берём контракт выше, планируем 1,5–2 дня бэка на чтение
  и удаление и отдельно обсуждаем список по устройству: без серверного токена он
  превращает анонимный `device_id` в ключ доступа к текстам вопросов. Экран делает
  фронт, как только ручка появится.
