# Нагрузочное тестирование

Оснастка готова, прогон не выполнялся. Ниже — что мерим, на чём и в каком порядке.

## Зачем

В проекте нет заложенной нагрузки: ни в ТЗ, ни в конфиге, ни в README. Оценка
сверху (по коду, без замера) даёт узкое место — `POST /guide/chat`, ~1.5–3 rps,
что соответствует примерно 100–150 одновременным посетителям с учётом пиков.
Прогон должен эту оценку подтвердить или опровергнуть.

Ключевое ограничение архитектуры, вокруг которого построены сценарии:

> `index.py:87` — `_loop.run_until_complete(app(scope, receive, send))` внутри
> **синхронного** `handler` поверх одного модульного event loop (`index.py:22`).
> Пока запрос обрабатывается, экземпляр функции занят целиком. Поднять
> `--concurrency` нельзя: параллельный вызов в потоке упрётся в
> `RuntimeError: This event loop is already running`.

Отсюда **throughput = число экземпляров ÷ латентность запроса**, и все сценарии
меряют именно латентность по путям плюс поведение на холодных стартах.

## Что уже написано

| Файл | Что делает |
|------|-----------|
| `scripts/loadtest_prepare.py` | Собирает `fixtures.json` с живого API, копирует фото, печатает предполётный отчёт |
| `lib/config.js` | Env-параметры, пороги, предохранитель от прода |
| `lib/fixtures.js` | Загрузка данных, генератор помеченных UUID |
| `lib/journey.js` | Путь посетителя: те же вызовы и порядок, что у фронта |

| `scenarios/ceiling.js` | Рампа по rps на один эндпоинт до отказа |
| `scenarios/visitor.js` | Профиль музея: лестница по одновременным посетителям |
| `cleanup.sql` | Удаление следов прогона из БД |

## Выбор стенда

**Прод не подходит** — и не только из-за нагрузки. События телеметрии по
требованию заказчика не удаляются (README, §«Аналитика посетителей»), поэтому
прогон навсегда добавит в отчёты сотни фальшивых визитов. `lib/config.js`
блокирует боевой хост API Gateway без `ALLOW_PROD=yes`.

Годные варианты по убыванию честности:

1. **Отдельная версия функции + отдельная БД.** Единственный способ померить
   реальные холодные старты Cloud Functions и реальную латентность до Managed
   PostgreSQL. Разворачивается как обычный деплой, но с копией схемы и seed.
2. **Локально через `docker-compose up`.** Меряет наш код и SQL честно, но не
   меряет главное — конкурентность 1 на экземпляр и холодный старт. Uvicorn
   локально обрабатывает запросы параллельно, цифры будут заметно оптимистичнее.
   Годится, чтобы поймать медленные запросы и ошибки до облачного прогона.

Внешние сервисы: если у стенда сняты `YANDEX_API_KEY`, `SPEECHKIT_API_KEY`,
`YOLO_ENDPOINT` — гид, озвучка и распознавание уходят в стабы (`llm.py`,
`tts.py`, `recognizer.py`). Наш код нагружается так же, денег не стоит, но
латентность внешних вызовов из результата исчезает. Поэтому: сначала стабы
(ищем свои узкие места), потом один короткий прогон с живыми ключами (ищем
потолок квот).

## Порядок прогона

### 0. Подготовка

```bash
BASE_URL=https://<стенд> python scripts/loadtest_prepare.py
```

Печатает, какие внешние сервисы у стенда живые, и собирает `fixtures.json`.
Прочитать предполётный отчёт **до** запуска k6 — там видно, будет ли прогон
стоить денег.

### 1. Проверка оснастки

```bash
k6 run -e BASE_URL=https://<стенд> -e TIME_SCALE=1000 loadtest/scenarios/smoke.js
```

Один посетитель, паузы сжаты в 1000 раз. Порог — ноль упавших запросов. Ловит
битый `fixtures.json`, 415 на фото, неверный `BASE_URL`. Дешевле поймать здесь,
чем через час прогона.

### 2. Холодные старты

```bash
k6 run -e BASE_URL=https://<стенд> -e BURST=30 -e WAVES=3 loadtest/scenarios/burst.js
```

30 посетителей открывают приложение одновременно, три волны. Смотреть на метрику
`first_request_ms` по волнам: первая — по холодным экземплярам, следующие — по
прогретым. Разница и есть цена холодного старта, которую платит толпа на входе.

Быстрый сценарий (~2 мин), внешних сервисов не трогает. Гнать первым из
«настоящих».

### 3. Потолок по эндпоинтам

Снизу вверх по цене:

```bash
k6 run -e BASE_URL=... -e EP=catalog     -e MAX_RPS=300 loadtest/scenarios/ceiling.js
k6 run -e BASE_URL=... -e EP=telemetry   -e MAX_RPS=300 loadtest/scenarios/ceiling.js
k6 run -e BASE_URL=... -e EP=search      -e MAX_RPS=100 loadtest/scenarios/ceiling.js
k6 run -e BASE_URL=... -e EP=tts         -e MAX_RPS=15  loadtest/scenarios/ceiling.js
k6 run -e BASE_URL=... -e EP=recognition -e MAX_RPS=10  loadtest/scenarios/ceiling.js
k6 run -e BASE_URL=... -e EP=chat        -e MAX_RPS=10  loadtest/scenarios/ceiling.js
```

Рампа идёт вверх ступенями и **сама останавливается**, когда p95 или доля ошибок
вылезают за отсечку (`abortOnFail`). Последняя пройденная ступень — потолок
эндпоинта.

`MAX_RPS` в примерах — от оценки. Если рампа дошла до конца без отсечки, потолок
выше: перезапустить с бо́льшим `MAX_RPS`.

### 4. Профиль музея

```bash
k6 run -e BASE_URL=... -e VISITORS=150 -e TIME_SCALE=6 \
    --out json=loadtest/artifacts/visitor-150.json \
    loadtest/scenarios/visitor.js
```

Лестница 25% → 50% → 100% → 150% от `VISITORS`. Ищем колено: ступень, на которой
p95 чата уходит вверх, а `http_req_failed` отрывается от нуля.

`TIME_SCALE=6` сжимает визит с 30 минут до 5 — вся лестница укладывается в ~45
минут вместо ~4 часов. Сжатие завышает rps на одного посетителя, поэтому
финальную цифру подтвердить одним прогоном на найденном значении с
`TIME_SCALE=1`.

### 5. Уборка

```bash
psql "$DATABASE_URL_PSQL" -f loadtest/cleanup.sql
```

Все `session_id` и `device_id` прогона начинаются с `10adfe57` — по этому маркеру
`cleanup.sql` их и находит. Пометить событие обычным полем нельзя: `props`
режется белым списком (`schemas.py`, §10).

Если ночной пересчёт (`cron 0 4 * * *`) успел посчитать день с нагрузочными
данными, после очистки перегнать агрегаты:

```bash
python scripts/rebuild_analytics.py --from <дата> --to <дата>
```

## За чем следить во время прогона

k6 показывает только клиентскую сторону. Одновременно смотреть:

**Экземпляры функции** (консоль Yandex Cloud → Cloud Functions → faberge-api →
Мониторинг). Ключевое: упёрлось ли число экземпляров в квоту. Если да — потолок
не в коде, а в квоте, и её надо поднимать:

```bash
yc serverless function get faberge-api
yc serverless function version get --function-name faberge-api
```

**Коннекты к PostgreSQL.** Пул в `app/db.py:14` заведён без параметров — дефолт
SQLAlchemy 5 + 10 overflow на экземпляр. Растёт числом экземпляров:

```sql
SELECT count(*) AS total,
       count(*) FILTER (WHERE state = 'active') AS active,
       count(*) FILTER (WHERE state = 'idle')   AS idle
  FROM pg_stat_activity WHERE datname = current_database();

SHOW max_connections;
```

**Логи функции** — на 5xx из гида: `UpstreamError` в `llm.py:170` ловит любое
исключение, включая 429 от YandexGPT. Отличить «квота» от «сервис лёг» можно
только по логам.

Заполнить по итогам прогона:

| Путь | p50 | p95 | p99 | Потолок, rps | Что упёрлось |
|------|-----|-----|-----|--------------|--------------|
| `GET /halls/{id}/exhibits` | | | | | |
| `POST /telemetry/events` | | | | | |
| `GET /search` | | | | | |
| `POST /speech` | | | | | |
| `POST /recognition` | | | | | |
| `POST /guide/chat` | | | | | |
| Холодный старт (`first_request_ms`) | | | | — | |

Итог — одно число: **сколько одновременных посетителей держит приложение до
того, как чат начнёт отдавать 5xx**. Считается от колена в сценарии 4, а не от
rps: посетителю rps не видны.

## Чего этот прогон не покажет

- **Реальный профиль посетителя.** Числа в `PROFILE` (`lib/config.js`) — гипотеза.
  После накопления боевой телеметрии сверить с `GET /admin/analytics/engagement`
  и `GET /admin/analytics/exhibits`, поправить.
- **Дашборд аналитики под нагрузкой.** Админские отчёты читаются из кэша
  `analytics_reports` (TTL 1440 мин) и почти бесплатны. Дорог ночной пересчёт
  `scripts/rebuild_analytics.py` на выросшей `events` — это отдельный замер, не
  HTTP-нагрузка.
- **Деградацию на длинной дистанции.** Таблица `events` растёт линейно и не
  чистится. Прогон на пустой БД не покажет, как поедет агрегация через сезон.
- **Размерные лимиты API Gateway.** Ответы функции через шлюз ограничены сверху;
  выгрузка `/admin/analytics/export` и загрузка медиа до 10 МБ в эти лимиты
  упираются отдельно от нагрузки. Проверять точечно, не рампой.
